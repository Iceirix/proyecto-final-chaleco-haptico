DOCUMENTACIÓN TÉCNICA · v1

Un FPS que se siente en el cuerpo

Sistema mecatrónico de inmersión para un juego de disparos en Unity: un guante de control lee tus gestos, un chaleco háptico te devuelve los golpes, y un ESP32 cose todo por WiFi en tiempo real. Este documento explica el hardware, el firmware y los códigos, línea por línea.

MCU: ESP32-WROOM-32 Enlace: WiFi AP · TCP 50 Hz Salidas: 4 motores · solenoide · Peltier · NeoPixel Entradas: 2 joysticks · flex · IMU · 4 botones Juego: Unity 6000.3

Sección 1

Visión general

El proyecto convierte un FPS de PC en una experiencia corporal. En lugar de teclado y ratón, el jugador usa un guante de control y viste un chaleco lleno de actuadores. Toda la interacción física pasa por una sola placa con un ESP32, que se comporta como puente entre el mundo físico y el motor de juego.

Los cinco subsistemas

  • Guante de control — 2 joysticks (mover + cámara), sensor de flexión como gatillo, IMU para el giro y botones de salto/recarga.
  • Guante háptico — un solenoide que golpea la mano simulando el retroceso del arma.
  • Chaleco háptico — 4 motores vibradores en cuadrantes (frente-izq, frente-der, espalda-izq, espalda-der) para el daño direccional.
  • Barra de vida — tira NeoPixel de 8 LEDs que muestra el HP con código de color.
  • Celda Peltier — un "golpe térmico" por evento de juego (vida crítica), manejado por un relé.
Contexto académico Proyecto Final de Temas Selectos de Mecatrónica (UNAM, 2026-2). El cerebro es un ESP32-WROOM-32 DevKit montado en una PCB casera; el firmware es un único sketch multiarchivo de Arduino y el juego es un proyecto Unity (TSPProyect/).

Sección 2

La clave del diseño es que el ESP es la fuente de verdad de las entradas (incluso decide qué arma está equipada, a partir del gesto de la IMU) y Unity es la fuente de verdad de los eventos del juego (cuánta vida queda, de qué dirección vino el disparo). Cada lado calcula lo que mejor sabe y se lo manda al otro ya digerido.

Sección 3

Electrónica y alimentación

Árbol de alimentación

Baterías 2×3.7 V
Litio en serie · ~7.4 V nominal (medido ~8 V con celdas a 4 V) · switch general
Regulador → 5 V
Alimenta la ESP32 y los relés de 5 V
ESP32 → 3.3 V
Joysticks, botones, flex e I2C de la IMU

La línea de 7.4 V cruda alimenta los motores y el solenoide; la de 5 V alimenta la lógica y los relés; la de 3.3 V (de la propia ESP) alimenta los sensores. Cada actuador de potencia se maneja con un transistor TIP120 (Darlington): el GPIO de 3.3 V satura la base y el TIP120 conmuta la carga a 7.4 V o el relé.

Por qué TIP120 y no el GPIO directo

Un GPIO del ESP32 entrega como mucho ~12 mA y 3.3 V — insuficiente para mover un motor vibrador, un solenoide o la bobina de un relé. El TIP120 actúa de interruptor de potencia: corriente pequeña en la base (GPIO), corriente grande en el colector (motor/relé). El diodo de protección del Darlington ayuda con los picos inductivos al apagar.

Reglas del ESP32 que mandan en el diseño
  • GPIO34/35/36/39 son solo-entrada → joysticks 2 y flex caen ahí naturalmente; GPIO39 no puede manejar un TIP120.

Sección 5 · Firmware

El loop principal

El firmware es un sketch multiarchivo de Arduino. Todos los .ino se concatenan en orden alfabético al compilar, así que no hay #include entre ellos: el estado se comparte por variables globales declaradas en GlobalState.h. El corazón está en ChalecoHaptico.ino y tiene un orden fijo cada iteración que no es casual.

ChalecoHaptico.ino · líneas 55–87copiar
void loop()
{
  dnsServer.processNextRequest();   // 1. responde el DNS captivo
  TryAcceptClient();              // 2. acepta Unity o redirige navegadores

  ReadInputs();                   // 3. joysticks, botones, flex
  ReadIMU();                      // 4. BMI160 + filtro + gesto de arma
  ReceiveCommandsFromUnity();     // 5. parsea KEY=VAL; del juego
  ReceiveCommandsFromSerial();    //    (mismo parser por el monitor serial)

  UpdateVibrationMotors();        // 6. aplica PWM y patrones de daño
  UpdateSolenoid();              //    pulsos no bloqueantes (millis)
  UpdatePeltier();
  UpdateHealthBar();

  unsigned long now = millis();
  if (now - lastSendMs >= SEND_PERIOD_MS)  // 7. envía a Unity a 50 Hz (20 ms)
  {
    lastSendMs = now;
    SendStateToUnity();
  }

  // El dashboard se actualiza DESPUES de mandar a Unity para no
  // retrasar la trama del videojuego. Lee los mismos globales.
  UpdateDashboard();                // 8. SSE a 25 Hz

  if (now - lastDebugMs >= DEBUG_PERIOD_MS) // 9. monitor serial a 5 Hz
  { lastDebugMs = now; DebugPrintAll(); }
}

Tres ideas de diseño importan aquí:

  • Prioridad a Unity. El envío de la trama del juego (paso 7) ocurre antes que el dashboard (paso 8). El dashboard lee las mismas variables globales, así que actualizarlo después no cuesta muestreo extra y mantiene la latencia hacia Unity al mínimo.
  • Nada bloquea. Solenoide, Peltier y patrones de daño usan millis(), nunca delay(). El loop debe correr libre a cientos de Hz para que el WiFi y el envío a 50 Hz no se atasquen.
  • Cadencias escalonadas. Unity a 50 Hz, dashboard a 25 Hz (la mitad), debug a 5 Hz. Cada cosa corre tan rápido como necesita y no más, repartiendo el CPU.
setup() — orden de arranque

En ChalecoHaptico.ino:38–53 se inicializan primero los pines y actuadores (todos a un estado seguro/apagado), luego el bus I2C y la IMU, y al final el WiFi y el dashboard. Poner los actuadores en LOW antes que nada evita que el chaleco "patalee" al energizar.

Sección 6 · Firmware

Entradas: joysticks y gatillo de flexión

Joysticks: normalización con zona muerta

Cada eje analógico (0–4095 del ADC de 12 bits) se mapea al rango [-1, 1] que Unity espera. Fíjate en el detalle del signo:

Inputs.ino · líneas 12–28copiar
  // Eje X invertido en ambos joysticks: el hardware quedo cableado
  // al reves y movia izquierda/derecha en sentido contrario.
  vrx1 = -NormalizeJoystick(analogRead(JOY1_X_PIN));
  vry1 =  NormalizeJoystick(analogRead(JOY1_Y_PIN));
  vrx2 = -NormalizeJoystick(analogRead(JOY2_X_PIN));
  vry2 =  NormalizeJoystick(analogRead(JOY2_Y_PIN));

  ApplyDeadzone();
...
float NormalizeJoystick(int raw)
{
  return mapFloat((float)raw, 0.0f, 4095.0f, 1.0f, -1.0f);
}

La inversión de signo en vrx1/vrx2 es la corrección de un cableado físico al revés — se arregla en software en vez de resoldar. La zona muerta (ApplyDeadzone, umbral JOY_DEADZONE = 0.20) fuerza a cero los valores pequeños, para que un joystick descentrado o con ruido no haga "caminar" al personaje solo.

El gatillo es un sensor de flexión, no un botón

Decisión de diseño: el disparo se calcula doblando el dedo. Esto se hace con histéresis para que no "tartamudee" justo en el umbral.

Inputs.ino · UpdateShootFromFlex() · líneas 38–59copiar
  // (rama FLEX_TRIGGER_WHEN_BELOW = 0: el ADC SUBE al doblar)
  if (!shoot && flexValue >= flexTriggerThreshold)
  {
    shoot = true;                                  // cruzó hacia arriba → dispara
  }
  else if (shoot && flexValue <= flexTriggerThreshold - FLEX_TRIGGER_HYSTERESIS)
  {
    shoot = false;                                 // soltó bien por debajo → deja de disparar
  }

El umbral es fijo (FLEX_TRIGGER_THRESHOLD = 1500 en GlobalState.h:49), no se calibra al arranque — una decisión deliberada para tener comportamiento repetible. La histéresis de 150 crea una banda: para encender hay que pasar 1500, pero para apagar hay que bajar a 1350. Sin ella, una lectura oscilando alrededor de 1500 dispararía decenas de veces por segundo.

Por qué dos ramas (#if) La macro FLEX_TRIGGER_WHEN_BELOW permite invertir la lógica si se cambia el divisor del flex por uno que lea al revés (resistencia que sube en vez de bajar al doblar), sin reescribir la condición. Es robustez ante un cambio de hardware probable.

Sección 7 · Firmware

IMU: ángulos y cambio de arma por gesto

La IMU es un BMI160 (acelerómetro + giroscopio) en I2C, dirección 0x69. El firmware la configura a mano escribiendo registros (no usa librería) y fusiona ambos sensores con un filtro complementario.

El filtro complementario, intuitivamente

El acelerómetro mide el ángulo absoluto pero es ruidoso y se altera con cualquier sacudida. El giroscopio mide la velocidad de giro: integrado da un ángulo muy suave pero que "deriva" con el tiempo. El filtro combina lo mejor de los dos:

IMU.ino · ReadIMU() · líneas 63–66copiar
  // Formula correcta: ang = beta*(ang + gyro*dt) + (1-beta)*accAng
  rollAngle  = BETA_COMP * (rollAngle  - gyrX * dt) + (1.0f - BETA_COMP) * accAngleXFil;
  pitchAngle = BETA_COMP * (pitchAngle + gyrY * dt) + (1.0f - BETA_COMP) * accAngleYFil;

Con BETA_COMP = 0.8: el 80 % del nuevo ángulo viene de integrar el giroscopio (suave, responde rápido) y el 20 % corrige hacia el ángulo del acelerómetro (ancla absoluta, mata la deriva). El dt real se mide con micros() cada ciclo, así la integración es correcta aunque el loop varíe de velocidad.

Bug corregido del sketch histórico El comentario en IMU.ino:9–10 documenta que el sketch viejo de Arduino IDE/IMU/ multiplicaba donde debía sumar en esta fórmula. Aquí está corregido — un buen ejemplo de por qué los sketches históricos son referencia pero no se reutilizan tal cual.

Cambiar de arma girando la muñeca

No hay botón de cambio de arma: se usa el pitch de la IMU con un patrón "inclinar y volver al centro". El ESP mantiene weaponIndex como índice absoluto y se lo manda a Unity; Unity solo obedece.

IMU.ino · UpdateWeaponFromPitch() · líneas 86–102copiar
  if (weaponGestureArmed)
  {
    if (pitchAngle >= WEAPON_PITCH_THRESHOLD)        // pasó +45° → avanza/retrocede 1 arma
    {
      weaponIndex = (weaponIndex + dir + WEAPON_COUNT) % WEAPON_COUNT;
      weaponGestureArmed = false;                  // desarma: no cuenta de nuevo aún
    }
    else if (pitchAngle <= -WEAPON_PITCH_THRESHOLD)
    {
      weaponIndex = (weaponIndex - dir + WEAPON_COUNT) % WEAPON_COUNT;
      weaponGestureArmed = false;
    }
  }
  else if (fabsf(pitchAngle) < WEAPON_PITCH_REARM)     // volvió a la banda central (±20°)
  {
    weaponGestureArmed = true;                       // rearma: listo para el siguiente giro
  }
}

La máquina de estados de un solo bit (weaponGestureArmed) es lo elegante: al cruzar ±45° cuenta un cambio y se desarma; solo vuelve a contar cuando el pitch regresa a ±20°. Así, mantener el control girado no cicla las armas sin control — exige el gesto completo de ida y vuelta. El % WEAPON_COUNT hace que el índice dé la vuelta (de la última arma a la primera). La dirección del giro se invierte con WEAPON_PITCH_INVERT en HardwareConfig.h.

Sección 8 · Firmware

Actuadores: el patrón "no bloqueante"

Todos los actuadores con tiempo (solenoide, Peltier, patrones de daño, parpadeo de la barra) siguen el mismo molde: guardan un instante de fin y comparan contra millis() cada loop. Nunca esperan. Despliega cada módulo:

Solenoid.inopulso de retroceso de 100 ms con cooldown▶

Unity manda SOL=1 en cada disparo. El firmware enciende el solenoide y agenda su apagado; ignora nuevos disparos hasta pasar el cooldown.

Solenoid.ino · 5–6, 19–32
const unsigned long SOLENOID_PULSE_MS = 100;     // dura el "golpe"
const unsigned long SOLENOID_COOLDOWN_MS = 160;  // descanso antes del próximo
...
if (solenoidTrigger && !solenoidActive && (long)(now - solenoidReadyMs) >= 0)
{
  solenoidActive = true;
  solenoidEndMs = now + SOLENOID_PULSE_MS;          // agenda el apagado, no espera
  digitalWrite(SOLENOID_PIN, HIGH);
}
solenoidTrigger = false;
if (solenoidActive && (long)(now - solenoidEndMs) >= 0)
{
  digitalWrite(SOLENOID_PIN, LOW);
  solenoidActive = false;
  solenoidReadyMs = now + SOLENOID_COOLDOWN_MS;     // arranca el cooldown
}

El truco del cast (long)(now - endMs) >= 0 hace la comparación robusta ante el desbordamiento de millis() (cada ~49 días): la resta en aritmética con signo siempre da el delta correcto.

Cada zona tiene dos modos. En reposo escribe el PWM continuo que pide Unity (motorTarget[i]). Cuando llega un golpe (DMG/HIT) ejecuta un patrón de 3 pulsos cortos sin bloquear, usando una pequeña estructura de estado por motor:

{

    if (damageZoneMask & (1 << (z - 1))) StartDamageTap(z);

El bitmask permite que HIT=3 dispare M1 y M2 simultáneamente (golpe frontal). El patrón de daño escribe siempre a intensidad máxima, pero pasa por WriteMotor() que lo recorta a 3 V (ver Sección 9).

Peltier.inogolpe térmico de 4 s + pulsos automáticos por vida baja▶

La celda Peltier reusa el relé que antes manejaba electrodos. Un pulso corto no se nota térmicamente, así que dura PELTIER_PULSE_MS = 4000. Lo más astuto: pulsa sola cuando la vida está crítica, sin que Unity mande nada extra — solo a partir del HP= que ya recibe.

Peltier.ino · UpdatePeltier() · 26–50
// Pulsos automáticos por vida baja: con 0 < HP < 30% pulsa sola
if (healthPercent > 0 && healthPercent < PELTIER_LOW_HP_THRESHOLD &&
    !peltierActive && (long)(millis() - peltierLowHpNextMs) >= 0)
{
  peltierTrigger = true;
}
if (peltierTrigger && !peltierActive)
{
#if ENABLE_PELTIER                       // bandera de seguridad: 0 = nunca cierra el relé
  peltierActive = true;
  peltierEndMs = millis() + PELTIER_PULSE_MS;
  digitalWrite(PELTIER_RELAY_PIN, HIGH);
#endif
}

El #if ENABLE_PELTIER es una bandera de seguridad: en 0, el firmware reconoce el comando pero nunca cierra el relé físicamente — útil para probar la lógica sin energizar la celda. Tras cada pulso, los pulsos automáticos esperan PELTIER_LOW_HP_COOLDOWN_MS (6 s) para dejar enfriar.

HealthBar.ino8 NeoPixel · color por HP · flash rojo de daño▶

Cada LED vale 12.5 %. El color cambia por umbral (verde >60 %, amarillo 25–60 %, rojo <25 %) y la tira se llena desde el último LED porque quedó montada al revés en el chaleco:

HealthBar.ino · DrawHealthBar() · 52–63
int litLeds = (hp * NEOPIXEL_COUNT + 99) / 100;   // redondeo al alza: >0% enciende ≥1 LED
for (int i = 0; i < NEOPIXEL_COUNT; i++)
{
  strip.setPixelColor(i, i >= (NEOPIXEL_COUNT - litLeds) ? color : 0);
}

El flash de daño es no bloqueante: UpdateHealthBar pinta toda la tira de rojo por FLASH_TOTAL_MS = 250 y luego fuerza un redibujo. También refresca cada 100 ms aunque el HP no cambie, para corregir LEDs corrompidos por ruido eléctrico en cables largos.

Sección 9 · Firmware

Límite de voltaje de los motores

Este es uno de los puntos más finos del proyecto. Los motores son de 3 V pero cuelgan de la línea de batería de ~7.4–8 V. Aplicar PWM al 100 % los quemaría. La solución: el firmware recorta el duty para que el voltaje promedio entregado nunca pase de 3 V, mientras el usuario sigue viendo un rango cómodo de 0–255.

El cálculo del techo seguro
VibrationMotors.ino · ComputeMotorMaxDuty() · 35–46copiar
void ComputeMotorMaxDuty()
{
  if (BATTERY_PACK_VOLTAGE <= MOTOR_RATED_VOLTAGE) { motorMaxDuty = PWM_MAX_DUTY; return; }
  int d = (int)lroundf((float)PWM_MAX_DUTY * MOTOR_RATED_VOLTAGE / BATTERY_PACK_VOLTAGE);
  // Con pack 8 V y motor 3 V → 255 * 3 / 8 ≈ 96
  motorMaxDuty = d;
}
El escalado en cada escritura
VibrationMotors.ino · WriteMotor() · 119–133copiar
void WriteMotor(int index, int duty)
{
  ...
  motorLevel[index] = duty;                       // guarda 0..255 "pedido" para el dashboard
  // Recorta el promedio a 3 V: 0..255 pedido → 0..motorMaxDuty físico
  int scaled = (int)((long)duty * motorMaxDuty / PWM_MAX_DUTY);
  analogWrite(motorPins[index], scaled);
}

Así, un M1=255 de Unity (100 % de intensidad) se traduce físicamente a un duty de ~96/255, que sobre 8 V promedia 3 V. El recorte cubre también los toques de daño, que llaman a WriteMotor con el máximo. Para reajustar tras medir la batería real, basta cambiar BATTERY_CELL_VOLTAGE en HardwareConfig.h — el techo se recalcula solo.

Sección 11 · Comunicación

WiFi: un puerto, dos protocolos

El ESP32 levanta un Access Point (ESP32_Chaleco / 192.175.5.1). El puerto 80 atiende tanto a Unity como a navegadores, distinguiéndolos por una heurística simple: husmea los primeros bytes.

WiFiAP.ino · LooksLikeHttp() · 119–127copiar
// Unity siempre lleva '=' temprano ("M1=128"); HTTP lleva un espacio
// temprano ("GET / HTTP..."). El primero que aparezca decide.
for (int i = 0; i < n; i++)
{
  if (sniff[i] == '=') return false;   // → es Unity
  if (sniff[i] == ' ') return true;    // → es un navegador
}

Si es un navegador, recibe un 302 → http://chaleco:81/ y se va al dashboard. Si es Unity, los bytes ya leídos se reinyectan al parser con FeedSniffedByteToUnity para no perder el primer comando. Detalles importantes:

  • El puerto 80 se atiende siempre, incluso con Unity ya conectado, para poder redirigir un navegador al dashboard con el juego corriendo. Solo se ignora un segundo socket de Unity.
  • DNS captivo en :53 resuelve cualquier nombre a la IP del AP, así tipear "chaleco" en el celular funciona aunque no soporte mDNS (y dispara el aviso de captive portal del sistema operativo).
  • mDNS publica chaleco.local.
No romper la heurística Al cambiar el protocolo de Unity, los comandos no deben empezar con espacio ni retrasar el primer =, o serían confundidos con HTTP. Es una restricción de diseño documentada.

Sección 12 · Comunicación

Dashboard web embebido

Un servidor HTTP independiente en el puerto 81 sirve una página de telemetría y control, todo a mano sobre WiFiServer (sin librerías, porque el AP no tiene internet). La página es una "consola táctica" (ámbar sobre charcoal) donde cada zona de motor es control y feedback a la vez.

Telemetría: Server-Sent Events

El navegador abre EventSource('/stream') y el ESP empuja un JSON con todo el estado a 25 Hz (SendDashboardFrame). Lee las mismas variables globales que Unity, así que no duplica muestreo.

Comandos: GET /cmd?c=…

Los comandos del dashboard reusan ProcessRxLine — el mismo parser de Unity. Arrastrar un slider de motor manda M#=valor en tiempo real.

Las dos lecciones de robustez de sockets

Este módulo encierra dos bugs difíciles ya resueltos, que el código defiende explícitamente:

  1. Keep-alive obligatorio. Las peticiones cortas van por slots con conexión persistente. Abrir una conexión TCP por comando agotaba los PCB de lwIP al arrastrar un slider (quedaban en TIME_WAIT) y lwIP terminaba matando el stream SSE o el socket de Unity. El JS además serializa los comandos (un fetch en vuelo, cola con coalescencia por clave).
  2. Sondeo con select() antes de escribir. A un cliente zombi (un celular que recargó la página) un write() lo reintentaría ~1 s y congelaría el loop entero (síntoma: uptime detenido, 0 Hz, Unity sin tramas). Por eso cada socket SSE se sondea con timeout cero y se desaloja tras 25 tramas sin drenar.
Dashboard.ino · SendDashboardFrame() · 398–417
int sockfd = dashboardClients[i].fd();
fd_set wset; FD_ZERO(&wset); FD_SET(sockfd, &wset);
struct timeval tv = {0, 0};                  // timeout cero: no bloquea nunca
writable = (select(sockfd + 1, NULL, &wset, NULL, &tv) > 0) && FD_ISSET(sockfd, &wset);
if (writable) { dashboardClients[i].write((const uint8_t*)buf, n); dashboardStreamStrikes[i] = 0; }
else if (++dashboardStreamStrikes[i] >= DASHBOARD_STREAM_MAX_STRIKES) /* desaloja */;

Funciona con varios dispositivos a la vez (cada /stream toma un slot en dashboardClients[]) y al mismo tiempo que el juego. El frame SSE incluye también el voltaje equivalente de los motores (campos vm/vb) para verificar el recorte de la Sección 9.

Sección 13 · Unity

El cliente TCP de Unity

WIFIConnectionScript.cs es el puente del lado del juego. Se conecta al ESP y deja los inputs en campos estáticos (J1X, Shoot, Weapon…) que cualquier otro script lee sin referencias cruzadas.

WIFIConnectionScript.cs · SetupSocket() · 65–80copiar
tcpClient = new TcpClient(host, port);
tcpClient.NoDelay = true;   // desactiva Nagle: cada comando sale YA
networkStream = tcpClient.GetStream();
streamWriter = new StreamWriter(networkStream);
streamReader = new StreamReader(networkStream);
secondaryThread = new Thread(RecieveData);
secondaryThread.IsBackground = true;   // no impide cerrar la app
secondaryThread.Start();

Dos decisiones críticas, ambas comentadas en el código como "no tocar":

1. NoDelay = true (sin Nagle)

El algoritmo de Nagle agruparía varios comandos pequeños antes de enviarlos, metiendo decenas de ms de latencia. Con NoDelay, un SOL=1 de disparo sale al instante — esencial para que el retroceso se sienta sincronizado con el clic.

2. Recepción con ReadLine() bloqueante puro
WIFIConnectionScript.cs · RecieveData() · 111–124
while (!abort)
{
  string line = streamReader.ReadLine();   // despierta apenas llega una línea
  if (line == null) { break; }              // la ESP cerró la conexión
  recievedData = line;
  string[] datos = line.Split(',');     // parsea el CSV por posición
  ...
}
No reintroducir el patrón viejo El código documenta por qué no usar DataAvailable + Thread.Sleep + mainThread.Send: ese patrón acumulaba ~500 ms de tramas viejas en el buffer del StreamReader, ataba la recepción a los FPS y producía inputs con retraso y estancados. El ReadLine() bloqueante en un hilo de fondo entrega cada trama apenas llega.

El parseo usa CultureInfo.InvariantCulture para que el punto decimal del CSV se interprete bien sin importar la configuración regional de Windows. El reparto al hilo principal usa mainThread.Post (no bloqueante) para no atar la recepción al render.

Sección 14 · Unity

Lógica de juego que dispara el hardware

Cada script de juego consume los inputs estáticos y, cuando ocurre algo, manda el comando háptico correspondiente.

FSPControllerScriptmovimiento y salto desde el joystick 1▶

Lee J1X/J1Y para el desplazamiento y Jump para saltar (FSPControllerScript.cs:47–50). El movimiento se aplica en FixedUpdate con CharacterController.Move, combinando vector horizontal y gravedad.

WeaponScriptdisparo → raycast + solenoide▶

El disparo se activa con WIFIConnectionScript.Shoot (el flex) o Fire1 para pruebas con teclado. En cada disparo manda el retroceso y hace el raycast al enemigo:

WeaponScript.cs · Shoot() · 105, 112–116
WIFIConnectionScript.SendData("SOL=1");   // retroceso háptico por disparo
...
if (Physics.Raycast(origin, direction, out raycastHit, 100f, LayerMask.GetMask("Enemy")))
{
  EnemyHealthScript enemyHealth = raycastHit.collider.GetComponent<EnemyHealthScript>();
  if (enemyHealth != null) enemyHealth.DamageEnemy(damageToEnemy);
}

Cada referencia opcional (animator, audio, fogonazo) se usa solo si está asignada — así una falta en el inspector degrada el efecto en vez de lanzar una excepción que pausaría el juego con "Error Pause".

PlayersHealthScriptdaño → bitmask direccional + vida▶

Convierte la posición del atacante en la máscara de zonas del comando HIT, en sectores de 90°:

PlayersHealthScript.cs · ComputeHitMask() · 38–47
Vector3 local = transform.InverseTransformPoint(attackerWorldPosition);
float angle = Mathf.Atan2(local.x, local.z) * Mathf.Rad2Deg;  // 0 = frente, +90 = derecha

if (angle > -45f && angle <= 45f)  return 1 | 2;   // frente: M1+M2
if (angle > 45f  && angle <= 135f) return 2 | 8;   // derecha: M2+M4
if (angle > -135f && angle <= -45f) return 1 | 4;  // izquierda: M1+M3
return 4 | 8;                                // espalda: M3+M4

Y manda golpe + vida en un solo paquete: "HIT="+mask+";HP="+health. Con NoDelay sale inmediato, y el firmware usa ese mismo HP para los pulsos de Peltier por vida baja.

SelectWeaponScriptobedece el índice de arma de la IMU▶

Cuando WIFIConnectionScript.Weapon (que calculó el ESP) difiere del arma actual, cambia de arma reusando el HUD y la animación existentes, y muestra la rueda un instante como feedback (SelectWeaponScript.cs:79–104). El ESP es la fuente de verdad; Unity solo sincroniza.

ReloadScriptPB2 → recarga táctica con cooldown▶

Detecta el flanco de subida de Button2 (PB2) y recarga munición con un cooldown, para que no sea munición infinita. Confirma con un pulso de solenoide. El juego usa un pool único de munición 0..100, sin cargador.
